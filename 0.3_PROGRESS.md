## Pairing UX — kryteria zakończenia

- `Generate Invitation` otwiera QR, kod i TTL w responsywnym modalu.
- Przychodzące `peerJoined`/`awaitingApproval` otwiera globalny modal Accept/Reject.
- Nazwa z `PairingOffer` przechodzi przez domain, SQLite i kontrakt do Fluttera.
- `rejected`, `cancelled`, `expired` i `completed` nie są renderowane jako aktywne zaproszenia.
- `approved` pozostaje widoczne do zakończenia bezpiecznej finalizacji.

## Ostatnia implementacja

- Kod kanoniczny ma dokładnie 6 znaków; parser nadal akceptuje spacje i myślniki.
- QR używa `torca://pair?v=2&code=ABC123&ticket=<128-bit hex>`.
- Relay wiąże ticket z ephemeral slotem; join z QR jest weryfikowany, a ręczny join bez ticketu pozostaje fallbackiem.
- Creator i joiner używają wspólnego kontekstu relay, więc nie rozjeżdżają się identyfikatory kontaktu/rozmowy.
- `pairing.create` zwraca `inviteUri` razem z `resourceId`; Flutter otwiera modal z dokładnie tym ticketem, a nie z rekonstruowanym URI.

## Relay availability hardening — in progress (2026-08-11)

- [x] Pairing and relay health now share one durable `TorRelayTransport`.
  Health requests reuse the pairing stream and only reconnect after a failed
  request, eliminating the former independent 15-second onion dial.
- [x] Relay health uses two consecutive failures before projecting `Degraded`;
  the first failure remains an observable retrying state with its typed code.
- [x] Contract v17 exposes the redacted runtime diagnostics buffer through
  `diagnostics.get`; Flutter no longer returns a hard-coded empty event list.
- [x] Relay state transitions are recorded as redacted diagnostics
  (`RELAY_CONNECTING`, `RELAY_CONNECTED`, `RELAY_DEGRADED`,
  `RELAY_DISCONNECTED`) rather than being inferred from the presentation LED.
- [x] Native actor maintenance is deadline-driven even while Flutter polls
  snapshots and notifications every 250 ms; pending operations can no longer
  starve waiting for an idle mailbox timeout.
- [x] Explicit create/join pairing attempts and their durable retries execute
  through the authoritative runtime transport. A separate relay probe is now
  observational and cannot veto those attempts.
- [x] The onion publisher remains alive after initial success. A service that
  stays degraded past a 75-second self-healing grace period is re-published
  with the existing Tor client rather than remaining degraded indefinitely.
- [x] Pairing worker owns its deadline-driven maintenance/poll clock; periodic
  runtime ticks never enter its mailbox, and an interactive command never
  blocks the runtime actor behind stale maintenance work.
- [x] `refresh_snapshot` is now read-only: it cannot initiate pairing publication,
  join, retry, or relay I/O on Flutter's 250 ms projection cadence.
- [x] Pending remote operations are reconciled separately, at most once per second,
  only after relay readiness and one operation at a time.
- [x] Interactive pairing waits up to 8 seconds for its worker result; this
  covers first Tor stream establishment while remaining below the runtime
  command timeout. Longer I/O remains retryable without freezing the actor.
- [x] Relay probing is an application-owned long-lived worker with one bounded
  request in flight, stable diagnostic codes and 5/15/30/60 s recovery backoff.
- [x] Onion address allocation is distinct from external onion reachability;
  runtime now projects `publishing`, `reachable`, `degraded` and `failed` rather
  than declaring the service ready as soon as an address is allocated.
- [x] Android coalesces bursty network-capability callbacks before waking the
  Rust supervisor, preventing normal route validation from creating reconnect storms.
- [x] Relay now starts its local broker before Arti bootstrap. Onion publication
  runs in a durable in-process worker, so a 60 s publication timeout recovers
  in place rather than terminating the container and restarting from zero.
- [x] Client-side onion publication is also isolated from Tor bootstrap and the
  runtime actor. A bootstrapped client attaches immediately; its endpoint is
  published by a bounded, retrying infrastructure worker.
- [x] `Publishing` and `Degraded` have independent recovery deadlines. A stuck
  publication now drops the actual Arti onion-service handle, retries twice
  with the preserved HSS identity, and then escalates to background Tor recovery.
- [x] Tor recovery swaps a stable `TorServiceHandle` shared by relay and peer
  adapters. Existing components no longer retain the client/runtime that failed.
- [x] The onion status observer no longer owns a second running-service handle,
  so dropping the lifecycle-owned handle really stops descriptor/introduction-point work.
- [x] SQLCipher retains memory security and ERROR diagnostics while setting its
  internal log level before key activation; best-effort `mlock` quota warnings no
  longer flood Windows and Android logs or obscure the real Tor lifecycle.
- [x] Relay no longer mistakes Arti's initial onion `Shutdown` status snapshot
  for a terminal shutdown. It retains the same Tor client through the
  subsequent `Bootstrapping` state instead of resetting publication work.
- [x] Docker liveness is a protocol health probe only. Endpoint allocation and
  public onion reachability are reported separately as `warming`/`ready`, and
  `relay_ready.txt` is reserved for externally reachable publication.
- [x] Deploy hashes only relay/Docker/Rust inputs and reuses an unchanged relay
  image; Flutter-only work no longer forces `docker compose up --build`.
- [x] Initial warm-up remains procedural: local listener → Tor bootstrap →
  Tor-dependent communication/pairing composition. It runs in the dedicated
  native startup worker, publishes progress, and never occupies the ABI actor.
- [x] A later Tor recovery bootstrap runs in its own single infrastructure
  worker. `RuntimeOwner::maintenance` now only harvests its result, so a slow
  Arti retry cannot freeze pairing, delivery, diagnostic snapshots or LEDs.
- [x] Added deterministic lost-response tests: idempotent relay operations are
  replayed once after reconnect, while `Close` deliberately remains
  non-replayable after an unknown outcome.
- [x] Deploy gates no longer parse `/proc/net/tcp` or require the endpoint file
  for container liveness. They execute the local relay protocol probe, while
  the endpoint file remains the public-address hand-off. Docker deploys also
  no longer delete that file merely because port 8844 is intentionally absent
  from the host network namespace.
- [x] Tor, relay and peer supervision are behind the application connectivity
  coordinator with typed state transitions and diagnostic history.
- [x] Connectivity supervisor regression coverage now deterministically
  injects a route-change failure, wakes the worker, and verifies recovery
  without waiting for the normal backoff interval.
- [x] The same supervisor coverage verifies the two-failure `Degraded`
  threshold and recovery back to `Healthy` after a network wake.
- [x] Relay readiness remains latched after proven reachability while Arti
  temporarily reports `Publishing`; a 75-second degraded grace window avoids
  false deploy failures while existing protocol connections remain healthy.
- [x] Deployment now waits for the public onion readiness marker after local
  relay liveness, so clients are not launched against an address that has only
  been allocated but is not externally reachable yet.
- [x] The deployment wizard separates `ClientsAndRelay`, `RelayOnly` and
  `FullReset` lifecycles. Relay-only maintenance does not enumerate devices,
  build, install, launch, clear client state or overwrite the last client
  deployment preset.
- [x] Relay `Restart` preserves onion identity and warm directory cache;
  `Repair` clears only relay directory cache; `Rotate` remains a deliberate
  endpoint-breaking operation and is forbidden in relay-only scope.
- [x] Full client reset explicitly warns that it removes persistent Arti cache
  and therefore forces a cold bootstrap. `torca-tor` diagnostics now report
  whether cache data existed at startup and the measured bootstrap duration.
- [x] The coordinated wizard can rebuild and repair the relay while preserving
  its onion identity, then deploy every detected Android and Windows client.
  `InstallPolicy=Always` now selects all deployable devices instead of silently
  retaining the manual subset, and forced relay rebuild is a distinct policy.
- [x] `deploy.ps1` without lifecycle arguments now opens a compact preset-driven
  wizard: fast client update, clean coordinated deploy, relay-only maintenance
  or custom advanced. The clean path derives all destructive/build/install
  policies and requires only configuration plus a final reset confirmation.
- [ ] Add deterministic end-to-end fault injection for relay startup, route
  changes and pending invitation completion (the transport lost-response cases
  are now covered without requiring a live Tor network).

### Manual E2E acceptance checklist

Run this after a clean coordinated deploy on one Windows and one Android
device. Do not reset data between the individual recovery checks.

- [ ] Relay container is `healthy`, `OnionReachable=True`, and restart count is
  zero before either client is launched.
- [ ] Both clients remain on the bootstrap surface until their first
  `NETWORK_READY` event, then expose Chats/Contacts/Invitations.
- [ ] Generate Invitation produces a QR/code; if the relay is temporarily
  unavailable, the modal closes with a queued message and the pending row is
  visible instead of trapping navigation.
- [ ] Restore relay reachability; the pending invitation completes without
  restarting either client and the QR/code appears in the Invitations list.
- [ ] Join from the other device; both clients receive the pairing completion
  notification and the contact/conversation is created.
- [ ] Trigger a route/network change; status may pass through Checking or
  Degraded, but recovers to Healthy without a reconnect storm.
- [ ] Collect diagnostics and verify `RELAY_CONNECTING`, `RELAY_CONNECTED`,
  `RELAY_DEGRADED`/`RELAY_DISCONNECTED`, and `NETWORK_READY` transitions are
  present with no secrets or raw payloads.

# Unified development wizard

- Added `scripts/wizard.ps1` as the single interactive entry point for run,
  redeploy, selective rebuild, full reset, Onion rotation, relay maintenance,
  status and all-device log collection.
- The wizard displays all detected devices and automatically targets every
  deployable device for the chosen platforms; per-device selection is no longer
  part of the normal workflow.
- Added explicit `Existing` client-artifact reuse and relay-image `Reuse`
  policies, keeping "run/redeploy current build" separate from source-aware
  incremental rebuilds.
- Onion rotation is an explicit destructive operation that automatically forces
  relay plus all-client rebuilds. Full redeploy keeps the existing Onion unless
  the dedicated new-Onion action is selected.
- Debug Windows and Android clients can now be launched directly from installed
  or built artifacts without invoking `flutter run` and rebuilding implicitly.
