## 2. Current production path

```text
Flutter
 -> canonical EngineGateway
 -> Bridge contract v9
 -> torca-native process handle
 -> process-owned NativeEngineRuntime
    -> ClientEngineActor
    -> RuntimeHost
       -> PairingDriver
       -> OwnedTorDriver
       -> TorcaCommunicationDriver
          -> ActiveRelationshipStore -> SharedPeerLink
          -> durable text/control workers
          -> inbound exactly-once
          -> read-state transaction
          -> relationship administration
          -> attachment transfer/export
```

Flutter does not own SQL, private keys, peer secrets, retries, pairing state machines, Tor lifecycle or attachment transfer state.

## 3. Persistence and migrations

`torca-storage-sqlite` is the canonical SQLCipher boundary. Operational SQL is external and parameterized.

Migration catalog: **1–17**.

Current durable invariants include:

- outbound message -> durable outbox ownership;
- atomic delivery state/attempt/timestamp synchronization;
- stale claim recovery after restart;
- exactly-once inbound dedup + message persistence;
- atomic receipt/message transitions;
- durable Delivered/Read control jobs;
- atomic MarkConversationRead + Read job creation;
- atomic Contact + Conversation + PeerCredential finalization;
- peer key bytes absent from SQL;
- persistent attachment metadata/progress;
- preparation failure -> Failed message + dead-letter outbox;
- Retry Now -> Queued message + Pending outbox;
- durable local contact aliases;
- uniqueness of live remote identity.

## 4. Pairing and trust

Pairing Protocol **v2** includes `display_name` inside the encrypted canonical `PairingOffer`. The signed transcript therefore binds:

- remote identity/key generation;
- remote display name;
- onion route;
- capabilities;
- pairing nonce/session context.

Flow:

```text
Create code/QR/torca://pair
 -> encrypted offer v2 exchange
 -> explicit approval
 -> Ed25519 transcript proof verification
 -> completion
 -> pairwise secret derivation
 -> protected peer secret
 -> atomic relationship commit
 -> signed display name persisted as local contact metadata
 -> relay/ephemeral cleanup
```

A second contact with an already-trusted remote identity is rejected. A trust replacement requires explicit Remove Contact and a new pairing.

## 5. Contacts and conversations

Implemented user operations:

- durable contact display name;
- local Rename Contact;
- Safety Number;
- Block / Unblock;
- Clear Conversation History;
- Remove Contact and local history/credential;
- Reply / Copy / Message Details;
- Retry Now for failed outbound messages.

Blocking closes ephemeral peer sessions and the peer-link sees only Active contacts for both outbound and incoming authentication.

Remove Contact clears durable message/control/attachment metadata, encrypted attachment cache/staging and the protected peer-secret handle.

## 6. Attachments

Implemented source path:

```text
picker
 -> Rust encrypted private cache
 -> durable chunk/progress state
 -> SharedPeerLink
 -> resume
 -> SHA-256 completion verification
```

Open/Save As performs Rust-side verified decrypt/export. Flutter never receives the encrypted cache path. Temporary plaintext Open exports use bounded controlled names; startup maintenance belongs to the runtime/storage side rather than presentation preferences.

## 9. Bridge v9 / Flutter

Contract version: **9**.

Schema and committed generated Dart source are byte-identical. Contract includes:

- identity/pairing/network state;
- contact alias, relationship/P2P state and Safety Number;
- messages with reply/timestamps/attempt count;
- Retry Now / MarkConversationRead;
- attachment progress/retry/cancel/export;
- relationship rename/block/unblock/remove/clear history;
- diagnostics.

The Flutter FFI implementation is one canonical `ffi_engine_gateway.dart` with one native presentation handle and one polling owner. Superseded `ffi_engine_gateway_v4.dart` and `ffi_engine_gateway_final.dart` were physically removed.

`torca-bridge` also uses the canonical Rust crate root `src/lib.rs`; the transitional `src/final.rs` root was removed.

## 10. PairingOffer v2 audit

The active `PairingOffer` constructors were audited after the v2 protocol bump:

- protocol round-trip test includes `display_name`;
- active pairing runtime includes local `display_name` in the canonical offer;
- the only v1 constructor without `display_name` was in superseded `pairing-coordinator/src/runtime.rs`; that source file was removed.

## 11. Dependency status

`Cargo.lock` is reconciled against the final local workspace dependency graph. The reconciliation changed only local `torca-*` dependency arrays; registry package versions, sources and checksums remain on the pre-existing pins after `BUG-040` restored the one accidentally altered checksum.

Flutter final source directly uses the packages declared in `pubspec.yaml`, including `app_links`, `shared_preferences` and `open_filex`. `launch_at_startup` is not used by current source and is intentionally not retained as a dead dependency.

A Flutter `pubspec.lock` does **not** currently exist in the repository and is not ignored by `.gitignore`. The implementation environment has no Flutter/Dart SDK, so a correct transitive lock cannot be fabricated here. The first owner `flutter pub get` from a clean checkout must generate the lock; inspect it for unexpected dependency drift and commit the accepted lock before closing the release reproducibility gate.
