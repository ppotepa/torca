## 2. Final source architecture

Production path:

```text
Flutter
   -> EngineGateway
   -> Bridge contract v4
   -> torca-native process handle
   -> process-owned NativeEngineRuntime
      -> ClientEngineActor
      -> RuntimeHost
         -> PairingDriver
         -> OwnedTorDriver
         -> TorcaCommunicationDriver
            -> SharedPeerLink
            -> durable text worker
            -> durable control/receipt worker
            -> inbound exactly-once
            -> read-state workflow
            -> attachment transfer
```

Flutter remains presentation-only. It does not own SQL, private keys, retry queues, pairing state machines, Tor lifecycle or attachment transfer state.

## 3. Persistence status

`torca-storage-sqlite` is the canonical SQLCipher storage boundary. Operational SQL lives in external `.sql` files and is parameterized.

Final migration catalog: **1–14**.

Key invariants now implemented:

- outbound message creation creates durable outbox ownership;
- outbox claim/reschedule/complete/dead-letter synchronizes message state, attempt count and timestamps;
- stale claims recover after restart;
- inbound dedup and message persistence are atomic;
- receipt insert and message lifecycle application are atomic;
- Delivered/Read control jobs are durable;
- contact + conversation + peer credential metadata finalization is atomic;
- peer secret bytes are not stored in SQL;
- attachment metadata/progress are durable;
- attachment preparation failure marks the message Failed and dead-letters the associated text outbox row.

`ControlOutbox` SQLCipher implementation was moved from the application crate into `torca-storage-sqlite`; `torca-control-delivery` now owns only the port/worker semantics.

## 4. Security / crypto status

Implemented in source:

- Ed25519 identity signing/verification;
- X25519 ephemeral pairing key exchange;
- HKDF domain separation;
- XChaCha20-Poly1305 protected pairing/peer payloads;
- canonical signed pairing transcript approvals;
- protected SQLCipher database key;
- protected identity key handles;
- protected pairwise peer-secret handles;
- Windows DPAPI and Android Keystore storage namespaces;
- no private/pairwise keys in Flutter DTOs or diagnostics.

Pairing relay capabilities/tokens are separate from public slot IDs. Relay state remains ephemeral.

## 5. Pairing status

User-facing flow is now:

```text
Create invitation
   -> Rust-generated code/TTL + QR URI
Join invitation
   -> code or QR
Encrypted offer exchange
   -> explicit Approve/Reject/Cancel
Signed transcript approvals
   -> completion confirmation
Pairwise secret derivation
   -> protected secret store
Atomic relationship commit
   -> Contact + Conversation + PeerCredential
Relay/ephemeral cleanup
```

`PeerProposal` never crosses Flutter. Pairing cryptography remains in Rust.

## 6. Messaging status

Normal communication is direct P2P over Tor after pairing.

Outbound:

```text
QueueMessage
 -> SQLCipher message/outbox
 -> DeliveryWorker
 -> SharedPeerLink reuse/connect
 -> authenticated peer handshake
 -> pairwise AEAD
 -> ACK
 -> durable state transition
```

Inbound:

```text
Peer Data
 -> authenticated decrypt/decode
 -> atomic dedup + persist
 -> durable Delivered receipt enqueue
 -> ACK
```

Stable envelope identifiers make retries duplicate-safe. `Accepted` and `Duplicate` ACKs both complete the sender delivery job.

## 7. Read receipts

Opening a conversation emits `MarkConversationRead`. Rust atomically marks eligible inbound messages Read and inserts durable Read receipt work. The same durable communication path sends Delivered and Read receipts.

## 8. Attachments

Implemented source path:

```text
Flutter file picker
 -> Rust prepare-from-path
 -> encrypted app-private cache
 -> persistent metadata/progress
 -> same SharedPeerLink
 -> bounded chunks
 -> resume offset
 -> SHA-256 completion verification
 -> finalization
```

Retry and Cancel are bridge commands. Progress is projected in the v4 snapshot. Dart never performs chunking or encryption.

## 9. Tor/runtime lifecycle

`OwnedTorDriver` owns the packaged Tor child process and restart policy. Production does not discover arbitrary Tor installs through PATH/Tor Browser.

Build/run/deploy stage:

- packaged Tor runtime;
- relay endpoint configuration;
- platform host overlays.

The process RuntimeHost owns Tor, pairing and communication workers.

## 10. Windows lifecycle

Implemented in source:

- single-instance runner guard;
- second-launch activation;
- close-to-tray;
- tray Show;
- real tray Quit;
- local notifications.

Important final ownership rule:

- `torca_engine_destroy` / normal gateway dispose releases a presentation handle;
- `torca_process_shutdown` is the explicit process-wide shutdown;
- Windows tray Quit invokes process shutdown before releasing the gateway/window.

## 11. Android lifecycle

Implemented in source:

- foreground service using `remoteMessaging`;
- process-scoped native RuntimeHost;
- Activity/Flutter-engine recreation does not stop the Rust runtime;
- JNI host supplies app-private runtime root, packaged Tor and relay configuration;
- service-level shutdown explicitly stops the process runtime.

## 14. Cargo.lock status

The final workspace path-package graph has been reconciled into `Cargo.lock` while preserving existing crates.io package versions/checksums.

A one-shot `cargo generate-lockfile` GitHub Actions attempt was created solely for deterministic lock refresh, but GitHub did not start the runner because the repository account was blocked by a billing issue. No workflow command ran. The temporary workflow was removed.

Because builds/tests were intentionally not executed during this implementation phase, owner validation should regenerate/check the lockfile once normal runner/network access is available and report any first concrete mismatch as a new `BUG-*`.
