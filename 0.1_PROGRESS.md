## 2. One-client refactor implemented on `main`

### Shared Flutter application

`apps/client` contains only the single `flutter/` application root. Windows and Android are targets of this same application rather than separate UI implementations.

The same UI code is used on every device:

- compact widths use routed screens;
- wide widths use a split conversation list + pane;
- both paths render the same `ConversationPane`;
- identity and pairing errors are handled through the shared gateway;
- native startup failure is visible and never silently falls back to memory state.

### Shared native transport

Added `crates/platform/torca-native`:

- builds `torca_bridge.dll` / `libtorca_bridge.so` as a `cdylib`;
- owns one `ClientEngineActor` and `EngineBridge`;
- exposes a narrow C ABI for identity creation, pairing start, message queueing and snapshots;
- uses explicit pointer/length UTF-8 arguments;
- returns presentation-safe result/snapshot JSON buffers;
- includes a committed C header and native contract tests.

Flutter uses `FfiEngineGateway` as the production transport. The previous duplicated Windows/Android engine MethodChannel implementations were removed.

### ClientEngine composition seam

`ClientEngine` is generic over inward-facing repository/key ports with in-memory implementations only as defaults. `ClientEngineActor` type-erases those implementation details through `EngineRuntime`, keeping `EngineHandle`, `EngineBridge`, FFI and Flutter non-generic.

### Developer workflow

The only public PowerShell entrypoints are:

```powershell
./scripts/build.ps1
./scripts/run.ps1
./scripts/deploy.ps1
```

Legacy format/validate/check/package/lock-refresh entrypoints were removed. Their mechanics live in `tools/build/Torca.Build.psm1`.

CI calls the same build entrypoint:

```powershell
./scripts/build.ps1 -Target check -CI
```
