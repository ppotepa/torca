## 4. Implemented capability summary

### Batches 01–06 — Foundation and local state

- Rust and Flutter workspace baselines, pinned toolchains and validation entrypoint.
- Shared IDs, bounded time, command/event envelopes and cancellation.
- Generic bounded wire framing.
- Local identity and profile lifecycle without private material in the domain.
- Compile-time SQL catalog, migrations and storage backend port.
- Crypto semantic types and provider interface with an explicitly insecure test provider.

### Batches 07–09 — Pairing, contacts, relay and engine

- Explicit pairing state machine with expiry and two-sided approval.
- Verified contacts, onion route/capability handles and block/remove lifecycle.
- One direct conversation per contact.
- Opaque, bounded rendezvous protocol and ephemeral in-memory relay.
- Single-writer `ClientEngine`, immutable snapshots and optional actor thread.
- Pairing completion coordinated by the engine to create contact and conversation.

Documentation:

- [`docs/0.1/PAIRING_CONTACTS.md`](docs/0.1/PAIRING_CONTACTS.md)
- [`docs/0.1/RENDEZVOUS_RELAY.md`](docs/0.1/RENDEZVOUS_RELAY.md)
- [`docs/0.1/CLIENT_ENGINE_BASELINE.md`](docs/0.1/CLIENT_ENGINE_BASELINE.md)

### Batches 10–11 — Messaging, receipts and durable delivery

- Bounded text messages and stable message IDs.
- Explicit queued/sending/sent/delivered/read/failed/cancelled transitions.
- Delivery attempt history and capped exponential retry policy.
- Separate idempotent delivered/read receipt domain.
- Conversation projections containing presentation-safe summaries.
- Transactional-outbox, due-work claiming, rescheduling and completion contracts.
- Inbound envelope deduplication and receipt/message SQL schema.

Documentation:

## 7. Current work package

### Batch 12 — Peer protocol

Required deliverables:

- authenticated handshake vocabulary and version negotiation;
- expected remote identity and capability proof fields;
- replay/freshness inputs and bounded payload kinds;
- protocol acknowledgements distinct from delivery/read receipts;
- codec test vectors and strict limits;
- no sockets, Tor process or message-domain state inside the protocol crate.

### Next exact action

Implement `torca-peer-protocol`, followed by transport-independent peer sessions and a Tor process/stream adapter.

## 9. Agent-side review notes

- Relay remains ephemeral and sees only bounded opaque blobs.
- Pairing domains contain no networking or persistence implementation.
- ClientEngine is the only coordinator that turns pairing completion into contact and conversation state.
- Message state and transport work are separate.
- Receipt application is monotonic and idempotent.
- Outbox and inbound dedup contracts are explicit.
- No claim is made that local validation passed.
