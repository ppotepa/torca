## 1. Working protocol

Every developer or agent must follow this sequence:

1. Read this file before changing the repository.
2. Read the linked scope, architecture and batch documents relevant to the current item.
3. Verify the current `main` state before starting.
4. Work on the current batch unless this file explicitly authorizes another item.
5. Keep the change small enough that `main` remains internally consistent.
6. Run the available repository validation command.
7. Update this file in the same commit as the implementation.
8. Record completed work, validation evidence, remaining work, blockers and the next exact action.

Do not maintain another live checklist. Detailed design belongs in `docs`, but implementation state belongs here.

### Status legend

- `[ ]` — not started;
- `[-]` — in progress;
- `[x]` — complete and validated;
- `[!]` — blocked;
- `[~]` — intentionally deferred from 0.1.

An item may be marked `[x]` only when its implementation, relevant tests, documentation and validation evidence have landed on `main`.

## 7. Accepted architectural decisions

The current implementation must follow these accepted decisions:

- modular monolith composed from focused mini-domain libraries;
- domain code independent from storage, transport, Flutter and FFI;
- `ClientEngine` as the single writer and workflow coordinator;
- parameterized SQL stored in `.sql` files;
- direct work on `main` during the 0.1 build-out;
- version-specific planning under `docs/0.1`;
- local devices own identity, keys and message history;
- relay remains an untrusted, ephemeral pairing broker;
- direct contact messaging uses Tor and does not depend on the relay.

Any change to these decisions requires an ADR and a corresponding update here.

## 8. Blockers and active risks

### Current blockers

None.

### Risks requiring attention during upcoming batches

- Keep foundation crates small; do not create a generic utility dumping ground.
- Prevent domain crates from depending on infrastructure implementations.
- Establish the final SQL layout before multiple repositories are implemented.
- Keep bridge contracts generated rather than duplicated by hand.
- Do not move workflow state into Flutter or platform hosts.
- Validate data durability at transaction and process-interruption boundaries.
- Avoid importing legacy code before reviewing its ownership and dependencies.

The detailed risk register is maintained in [`docs/0.1/RISKS.md`](docs/0.1/RISKS.md).
