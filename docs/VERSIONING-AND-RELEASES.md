# Versioning and releases

Torca separates the **product version**, **artifact build number** and several **compatibility versions**. They answer different questions and must not be collapsed into one number.

The canonical release metadata file is [`../release/version.json`](../release/version.json). Rust and Flutter metadata mirror parts of it for their respective build systems.

## Version axes

| Axis | Primary location | Meaning |
| --- | --- | --- |
| product version | `release/version.json.version` | human-facing SemVer/pre-release identity of the Torca product |
| build number | `release/version.json.build` | monotonically increasing packaging/build identity for artifacts of a product version |
| release channel | `release/version.json.channel` | development channel such as alpha/beta/stable |
| contract schema | `contractSchema` + canonical generated contract | compatibility of the Flutter/native presentation contract |
| native ABI | `nativeAbi` + native interface | compatibility of the native host ABI |
| storage epoch | `storageEpoch` + storage compatibility code | coarse compatibility boundary for installed durable data; incompatible epochs are rejected explicitly |
| wire version | `wireVersion` + protocol code | release-level wire compatibility marker; protocol-specific version rules remain owned by protocol crates |
| schema version | `schemaVersion` | release/artifact schema compatibility marker propagated into deployment manifests |

Exact current numeric values should be read from source rather than copied into prose.

## Product version synchronization

For a release candidate, these values must describe the same product version:

```text
release/version.json.version
Cargo.toml [workspace.package].version
apps/client/flutter/pubspec.yaml version before +<build>
```

The Flutter suffix `+N` is the artifact build number. It can change while the product SemVer stays the same.

Example shape:

```text
product: 0.2.0-alpha.0
build:   1
Flutter: 0.2.0-alpha.0+1
```

The example explains the relationship only; the source files are authoritative for current values.

## Pre-1.0 policy

Torca is pre-1.0 and can make incompatible product changes between minor versions. Use normal SemVer intent while keeping alpha maturity explicit:

- increment the pre-release identifier (`alpha.0` -> `alpha.1`) for a new candidate of the same planned product version;
- increment patch/minor when the product version itself changes according to the scope of the release;
- increment the build number for a newly packaged artifact when the product version does not need to change; and
- never use a higher version number as a substitute for release evidence.

Compatibility versions may need to move independently even when the product SemVer does not. A contract/storage/wire/ABI breaking change must update its owning compatibility marker and migration/rejection behavior in the same change.

## Changelog

[`../CHANGELOG.md`](../CHANGELOG.md) starts with an `Unreleased` section. Record notable user/developer/security/compatibility changes under:

- Added
- Changed
- Fixed
- Removed
- Security

At release time, move the relevant `Unreleased` entries under the exact product version and release date, then recreate an empty `Unreleased` section. Do not reconstruct fictional historical releases from old plans or commit messages.

## Tags and release commits

Release tags should use the product version with a `v` prefix, for example `v0.2.0-alpha.0`, and identify one immutable commit.

A release should be cut from a known clean commit with synchronized version metadata. The release record should capture at least:

- commit SHA and tag;
- product version + build number;
- target platform/architecture/configuration;
- compatibility metadata from `release/version.json`;
- artifact hashes/provenance generated by packaging;
- the exact automated/platform/device evidence actually executed; and
- known accepted risks/limitations.

Do not tag or describe an artifact as audited, device-validated, signed or release-ready unless that evidence exists.

## Compatibility changes

### Presentation contract

When the generated Flutter/native contract changes incompatibly, bump the contract schema and regenerate/check both sides in the same change. Generated Dart is not an independent version source.

### Native ABI

A breaking native symbol/signature/ABI change requires a native ABI bump plus matching host packaging. Runtime/library mismatch must fail explicitly rather than being silently retried or substituted.

### Storage

Normal schema migrations can evolve within a compatible storage epoch. The storage epoch is for deliberately incompatible installed-data generations. A mismatched epoch is rejected before migrations reinterpret old data; reset/migration policy must be explicit.

### Wire/protocols

The release-level wire marker and protocol-specific versions are compatibility contracts, not marketing versions. Protocol crates own exact framing/version acceptance and bounded inputs. Changes must be tested against supported/unsupported versions rather than inferred from the product SemVer.

## Release readiness is separate from versioning

Version synchronization proves only that artifacts identify themselves consistently. Release readiness additionally depends on the validation/security/signing requirements described in [`STATUS.md`](STATUS.md), [`TESTING.md`](TESTING.md), [`OPERATIONS.md`](OPERATIONS.md) and [`../SECURITY.md`](../SECURITY.md).
