# Torca 0.3 — plan implementacji granic architektonicznych

Wydanie 0.3 domyka Dependency Inversion pomiędzy application, infrastructure i platform.
Nie przebudowuje poprawnego grafu domen ani nie mnoży crate’ów bez potrzeby.

## Zrealizowane etapy

1. Guardrails dla grafu Cargo i zakazów źródłowych, bez listy tymczasowych wyjątków.
2. Typed application vocabulary dla peer statusu i inbound envelope; Tor driver przeniesiony
   do infrastructure.
3. Atomowy plan `mark read` przygotowywany przez application oraz jedna domenowa reguła
   deterministycznego `ReceiptId`.
4. `ClientApplicationRuntime` jako façade dla komend, readiness, bootstrapu i projekcji.
5. Breaking contract v16: DTO/schema/serde oraz czyste mapowanie application → wire.
6. Native jako composition/ABI/JNI z jednym application runtime, bez `ContractRuntime`.
7. Aktywne domeny presence i notifications; hosty renderują gotowe intencje.
8. Flutter używa `resourceId`, wygenerowanych enumów pairingu i protocol-owned `inviteUri`;
   nie dedukuje rezultatu use-case’u przez wybór ostatniego elementu ani różnicę snapshotów.
9. Pełny audyt Rust, Flutter, generatora, policy oraz buildów Windows i Android.

## Inwariant 0.3

- domains/protocol nie zależą od application, infrastructure ani platform,
- application nie zależy od infrastructure ani platform,
- versioned external representations należą do protocol/contract,
- repositories wykonują persistence i transakcje, ale nie podejmują product policy,
- contract nie wykonuje use-case’ów, readiness ani algorytmów security,
- native posiada composition i lifecycle procesu, a nie application workflow,
- Flutter posiada presentation i transient view state, ale nie protokół ani state machine.

Szczegółowe wyniki bramek i stan wydania są w [`0.3_PROGRESS.md`](0.3_PROGRESS.md).
